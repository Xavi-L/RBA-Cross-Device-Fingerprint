**6. 分组、标签与数据使用规则**

891 是覆盖统计单位。用于防止信息泄漏的分组要更保守：同一已核验设备、同一安装、同一画像的重复记录和同一攻击 scenario 放在同一集合；做跨型号泛化时，建议同一厂商＋型号的不同系统版本也整组分配。跨系统外推可另设明确实验，不能把它和跨设备泛化混为一谈。

有 MTC 平台设备 ID／执行清单时，用它补充可验证映射；没有时只能标为安装或设备画像，不宣称物理设备身份。型号别名与厂商大小写先保留原值，再用有依据的映射规范化。7 月采集的平台总目录不是本次 900 条采购清单。

重复记录不从原始库删除。主覆盖表每个组合只计一次；逐会话运行结果保留，汇总时按组归一或使用预先固定的代表记录策略；重复记录另用于组内变化分析。不能选“最容易通过规则”的那次采集。

初始可沿用现有约 70／15／15 的整组发现／开发／最终验证比例，但实际分配由 QC 后组数、厂商与系统覆盖决定，并在挖掘前冻结。稀有系统或只有一两条的浏览器类别允许仅做描述，不强行分层计算稳定指标。现有每 split 至少 5 组是程序准入下限，不代表统计证据充分。

应把准入拆成三个问题：

- **规则发现可用**：结构可解析、有可靠字段状态、可保守分组；可在无攻击标签的参考样本上发现一致性候选。
- **参考集验证可用**：有本轮采集过程与无主动干预的记录，可报告观察到的告警与不确定性；未经核验不能称为已证实无攻击的负例。
- **检测效果可用**：有独立事实标签、已核验干预／可观察影响、可信分组和隔离的测试集，才能计算对应任务的检测指标。

现有 latest experiment gate 对监督主任务要求两类标签；不能伪造标签来让正常参考集通过它。需要新建或明确区分只做规则发现的任务入口。

新 MTC 数据不能仅因来自真机平台就全部标为“安全／低风险”。ADB、debuggable、云测安装来源、代理等可能是采集上下文，应与跨层矛盾分开。LLM 评分、规则报警和 Browser 字段差异均不能反过来作为同一系统的真实标签。

本次使用全量数据做结构与字面比较诊断，没有挖掘阈值或正式规则。后续一旦按具体模式挑规则，接触过的材料应进入发现／开发范围；最终集不能在看过结果后反复参与修改。

**7. 新规则发现的具体路线**

先做字段清单：每个字段记录数据类型、单位、状态、默认哨兵、采集环境、API／内核适用范围、同名跨端可比性。至少区分“严格可比”“归一后可比”“有容差可比”“只在特定环境可比”“不应跨端直接比”。

不进行无约束的 244×244 全组合搜索。先按语义预定义候选关系，使用可解释的条件频数、离散兼容表、数值残差／分位数区间和重复观测稳定性来筛选。可先筛 6–8 个规则家族；最终晋级数量由结果决定。

| 优先级／规则家族 | 使用的新证据 | 主要方法 | 必须覆盖的反例与限制 |
|---|---|---|---|
| P1：OS／UA／容器 | Native OS、WebView provider／默认 UA、App Web UA、Browser UA | 分辨 UA 类型、reduction、内核版本与容器；检验语义兼容 | 系统 UA reduction、定制 UA、内置浏览器不可与 WebView 强制等版本 |
| P1：屏幕／DPR | Native 屏幕尺寸、App 与 Browser screen／DPR／viewport | 先统一单位与横竖屏，再分析受条件约束的残差 | 折叠屏、分屏、显示缩放、状态栏；viewport 高度不应要求等于物理高度 |
| P1：GPU 语义 | Native GLES／EGL renderer、App／Browser WebGL vendor／renderer／capability | 厂商／渲染后端归一、条件兼容表和明确冲突 | ANGLE 包装、软件回退、浏览器屏蔽；不能仅 renderer 字符串不同就报警 |
| P1：App Web–Browser 共同属性 | 时区、语言、触点、平台、hardwareConcurrency 等 | 字段特定兼容与差异分布；区分环境变化与物理约束 | 浏览器独立语言设置、核心数限制、首次启动、时序变化 |
| P2：内存与能力 | Native 总内存、App／Browser deviceMemory、API 支持状态 | 量化／封顶语义和条件区间，先排除 0 哨兵 | 内存近似值不能精确对齐；不同实现上限不能直接迁移 |
| P2：传感器结构 | 数量、类型表、各类 has_*、厂商／API | 结构自洽与能力缺失候选，保留设备族例外 | 某传感器不存在不等于攻击，云真机环境与硬件差异不能成为通用高危规则 |
| P2：插件、字体、Canvas、Audio | 两端同名指纹、浏览器／WebView 内核信息 | 先做版本条件下的组内稳定性和变化归因 | 高比例正常差异、隐私策略与哈希算法／渲染差异；不先承诺严格相等规则 |
| 暂缓：长期电池／性能规律 | 重复采集的电量、温度、耗时、网络等 | 需要计划化时间序列与受控负载 | 现有少量短时重复不足以证明长期死值、恒定功耗或机房规律 |

每条候选至少保存：规则 ID 与版本、发现数据版本和 split、原始字段路径、执行所需表面、表达式、单位与容差、独立支持组数、适用分母、反例及集中出现的环境、官方语义依据、经验校准来源、执行状态和审阅结论。

发现集提出候选；开发集检验反例并固定条件；最终集只检验已经冻结的规则。不能因为最终集出现反例就回头调整阈值后仍沿用同一正式测试名义。

支持度按组计算，而不按 1,029 条 session 直接计。建议预先约定候选筛选门槛，例如全局候选需多个厂商、至少数十独立画像支持；设备族规则允许范围较窄但必须明确标记。P2 已预先固定工程筛选下限：全局经验候选需发现／开发至少 30／10 个可评估分组及 3／2 个厂商；限定范围经验候选需至少 10／5 个分组。低于下限只作描述性候选，通过下限也不等于规则正确或统计证据充分；不能为凑规则数量或旧效果临时降低。

目录保存 official_document 与 device_mined_rule 的来源区分；官方派生关系仍标明是项目推导。凡使用 MTC 数据拟合容差的关系，额外记录经验校准来源，不能继续描述为纯官方、不依赖数据的关系。

推荐主实验先完成 E0–E7，E8 不阻塞规则和跨端主线。RF／MLP／ElasticNet 不包含在这个核心矩阵中。

E2 与 E3 必须分开：先固定 App177 比较规则版本，再固定新规则比较 App177／Full244，才能区分“规则重建收益”和“多了一个输入表面的收益”。主结果还应包含 Full244 去掉跨端关系的对照，检验增益是否来自关系，而只是某个 Browser 单字段。

固定规则输入消融不是“为每个单端单独优化后的最佳检测器比赛”。若某个单端没有适用规则，应报告 NOT_EVALUATED；不能据此宣称该端没有价值或跨端天然胜出。更多输入也可能增加告警、误报或不确定性，均保留。

正式指标分三层：数据层报告接受／排除／缺失；规则层报告可评估、冲突、上下文与未知；具备事实标签后，才对具体任务报告 TPR／FPR／Precision／Recall／F1 等。每项同时给全 cohort 数与适用分母，不静默剔除拒判和失败。主要汇总按设备／画像组计，逐 session 结果作辅助；区间估计和重采样也按组进行。

只有正常参考样本时，不能评估攻击召回。不同知识轨报警相同也不能证明知识等价；已有攻击覆盖不足时，应报告“当前场景未体现增量”。

**9. 新两态攻击数据应怎样补**

继续采用用户此前确认的 baseline → attack_active 两态协议，不把 clean_post 重新变成必做要求。

每个阶段均要尝试 App177＋Browser67；成功时保存各自 raw、receipt、pair provenance；失败时记录具体阶段、原因和保留表面。不将旧攻击 App 与新 MTC Browser 拼成一条样本，也不将离线修改 JSON 当成真实工具干预。

覆盖对象按可实际执行的干预分组：App Web 定向操纵、独立 Browser 定向操纵、已支持的 UA／platform／图形或其他属性干预，以及不应导致身份异常的环境变化对照。新增工具能力先用少量设备确认；未经执行验证的能力只列候选。

先选择约 6–10 个开发画像做协议试跑，覆盖低／中／高 API 和多个浏览器家族，验证两端时间与标签能对上；正式实验样本量再由目标攻击族、独立组数与所需不确定性范围确定。不能用大量同一模拟器重复运行替代独立设备。

逐场景分别保存：干预是否成功、目标字段是否真正发生变化、规则是否适用、是否产生报警。工具运行成功但目标字段未变化，不能当该规则应检出的正例；保留在工具执行／可用性统计。传输路径干预单独报告，不自动成为指纹字段操纵正例。

MTC 参考集提供正常环境覆盖，不会自动提供 891 个可运行攻击的设备。若实际没有权限／条件补采独立 Browser 攻击，本轮仍可完成新参考集 QC、经验关系发现、App177 历史回归与正常差异分析；Full244 的检测增益明确待验证。
