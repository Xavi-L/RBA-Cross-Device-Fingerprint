| 方案项 | 判断 | 原因和条件 |

### 2.1 内存、并发与 swap

下表是小规模采集的初始预算，不是该 Linux 镜像的实测值：

| 项目 | 建议预留 |
|---|---:|
| Ubuntu 基础服务 + Docker daemon | 400–700 MiB |
| Nginx | 20–80 MiB |
| 单 worker Python + 当前量级会话状态 | 150–400 MiB |
| 其余内存 | 文件缓存、突发连接、部署与备份余量 |

因此 2 GB 可以起步。若还要运行 PostgreSQL，可再预留数百 MiB 并限制连接、工作内存；此时升级 4 GB 比挤压所有进程更稳妥，但本项目首期没有这个必要。

可以准备 1–2 GiB swap 应对短暂峰值，不能依赖持续换页维持采集。APK 构建、pandas/RF/MLP、批量数据导出不在这台机器执行；尽量在部署前构建好镜像，至少不要在付费采集高峰构建。

“累计 300 台”不代表“同时 300 台”。Browser 页面每两秒轮询一次；仅 100 个等待中的页面就约 50 次状态请求/秒，另有 App 轮询、阶段回执和上传。全量 JSON 重写与 `fsync` 会阻塞当前 event loop。建议用隔离目录按 10/30/100 个并发流程递增试验，检查 p95 时延、5xx、超时、重复抑制和 completed 关联；具体上限按实测定，不能先承诺数百并发。

### 2.2 数据库选择与最小模型

推荐分成两个独立里程碑：

- 本次 HTTPS/云端迁移：保持 JSONL 合同，修正已发现的持久化/恢复问题，不同时重写 collection pipeline。
- 持续采集或扩大并发前：优先评估 SQLite 的元数据事务化；只有确实需要多进程/多主机写入、复杂远程查询和独立 DB 运维时再选 PostgreSQL。

SQLite 对单机单写者很合适，但 WAL 仍然只有一个 writer，需要短事务、超时/忙重试和正确备份，不能当成无限并发开关。[SQLite WAL 文档](https://www.sqlite.org/wal.html)

若以后使用 SQLite/PostgreSQL，按当前合同推导的最小模型应是：

| 逻辑实体 | 保留什么 | 关键边界 |
|---|---|---|
| batch | 进程批次 ID、开始/结束、关闭原因 | 继续明确它不是 MTC run ID。 |
| capture | canonical App/Browser payload 的身份、类型、hash、schema、时间、raw 引用 | observation 与重试请求分开；不要仅用 session_id 去重不同 payload。 |
| receipt | 每次 App HTTP 接收回执、capture 引用、duplicate/warnings | 重试可产生新 receipt，不产生新 observation；兼容现有 Browser receipt 标识。 |
| browser_pair | request ID、session、App receipt/capture、Browser capture/receipt、状态、阶段时间、token claims 标识 | 唯一性至少覆盖 `(batch_id, ticket_request_id)`；保留 provisional 状态与幂等冲突规则。 |
| event | 批次/配对状态变更和审计事件 | append-only；避免把可变状态当历史证据。 |

session 可以先由 captures 建索引和派生，不必立即单建一张表；artifact 可先作为 capture 的 raw 引用字段，provenance 可由不可变关联导出，也不必机械增加同名表。没有经验证的物理设备 ID，不建议先设计会误导研究口径的 `device` 主表。

本项目 raw payload 中位数仅约 12–22 KB。未来 SQLite 可直接在同一事务存 canonical JSON、receipt 和 pair 更新，再异步导出 JSONL，避免 DB+文件双写。若坚持 raw 文件为权威，必须明确“先写临时文件并持久化/原子落位，再提交 metadata”，并能清理孤立文件、检测缺失文件；JSONL 导出需要可重放的记录 ID。PostgreSQL 与文件系统也没有天然的跨系统事务。

## 3. HTTPS compatibility review

### 3.1 本次取得的直接证据

|---|---|---|

| android-6.0.0_r1 | 存在，同上 | 存在，同上 |

从官方公开 PEM 提取 ZeroSSL RSA intermediate、R46-by-USERTrust、USERTrust-by-AAA 后，用上述各版本的单独信任根做了六次 `openssl verify`：三个版本、两种路径均为 `OK`。

**这验证的是公开 CA 签名路径，不是域名证书或手机握手。** 目前没有 `collect.example.com` 对应的真实 leaf、服务器或目标真机验证，也未检查每台 OEM ROM 的实际 trust store。不能宣布 5.1.1/6/7 已全兼容。反过来，也不能笼统声称 Android 5.1.1 全部缺 USERTrust、必须接 AAA。

### 3.2 推荐的 leaf、intermediate 和 fullchain

第一候选是短链，适用于目标实际信任 USERTrust 的浏览器：

```text
服务器发送，按顺序：
  1. collect.<真实域名> 的 RSA leaf，SAN 匹配域名、serverAuth、SHA-2 签名
  2. 这张 leaf 的实际签发 intermediate
     当前 ZeroSSL 候选为 ZeroSSL RSA DV SSL CA 2
  3. Sectigo Public Server Authentication Root R46
     issuer = USERTrust RSA Certification Authority（交叉签名版）

客户端本地信任锚：
  USERTrust RSA Certification Authority（自签根）
```

若某款 OEM 浏览器不信任 USERTrust、但信任 AAA，则验证扩展链：

```text
服务器发送：
  leaf
  -> 对应 intermediate
  -> R46，由 USERTrust RSA 签发
  -> USERTrust RSA，由 AAA Certificate Services 签发

客户端本地信任锚：
  AAA Certificate Services（自签根）
```

Nginx 的 `ssl_certificate` 应指向按上述顺序组装的 fullchain：leaf 在前，随后是真实关联的 intermediates/cross-signs。通常不发送最终自签根；发送根不会让客户端自动信任它。`ssl_trusted_certificate` 也不能代替实际发送给客户端的 fullchain。[Nginx HTTPS 配置](https://nginx.org/en/docs/http/configuring_https_servers.html)

必须避免：

- 用 R46 自签版替代 R46-by-USERTrust：旧系统不认识新的自签根，链会断。
- 在 self-signed USERTrust 后随意拼 AAA：需要的是 issuer=AAA 的 USERTrust 交叉签名证书。
- 拼接不匹配的旧 intermediate、不同 key 的同名证书或过期 AddTrust 路径。
- leaf 续签后仍盲用旧 bundle：实际 issuer 可能已经变化。

正确的扩展链不应天然损害现代 Chrome；现代客户端通常能在其已信任的 USERTrust/R46 处建链。但仍须验证现代 Chrome 的实际路径和当前根计划约束。不能仅以证书 `notAfter` 推断它在所有浏览器中会一直被信任。

AAA 路径的相关根及本次检查的 USERTrust-by-AAA 证书到期于 **2028-12-31**，是需要提前退出或替换的兼容路径，不是永久方案。AAA 根的 SHA-1 自签名也不等于应该签发 SHA-1 leaf 或降低服务器整体安全级别。

### 3.3 TLS、cipher 与 Ubuntu/OpenSSL

起始配置可保持：

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-RSA-AES128-GCM-SHA256:ECDHE-RSA-AES256-GCM-SHA384;
ssl_ecdh_curve X25519:prime256v1:secp384r1;
```

这里 `prime256v1` 保留旧客户端常见的 P-256；不要只允许新曲线。TLS 1.3 cipher 不由上述 `ssl_ciphers` 列表控制。只部署 RSA leaf 时原模板的 ECDSA suites 不是兼容性的关键。

如果真实 ClientHello 证明某个目标只能共同支持 ECDHE-RSA AES-CBC，再定点追加 `ECDHE-RSA-AES128-SHA256` 或 `ECDHE-RSA-AES128-SHA` 并复测；后者的 SHA-1 是记录 MAC，与 SHA-1 证书签名不是一回事。当前没有证据要求默认开放静态 RSA、TLS 1.0/1.1、3DES/RC4，或设置 `SECLEVEL=0`。

Ubuntu 24.04 本身不是旧 Android 失败的充分原因。重点核对实际 Nginx 镜像的 `nginx -V`、所链接 OpenSSL、安全级别、signature algorithms、曲线和目标 ClientHello。OpenSSL 的安全级别会约束算法与密钥，不能只检查 cipher 名称。[OpenSSL security level](https://docs.openssl.org/3.2/man3/SSL_CTX_set_security_level/)

### 3.4 必须补齐的验证

1. **签发后证书检查**：SAN、key type、issuer、期限、完整路径；以 AOSP/OEM 根集独立验证，不能只用桌面默认 CA store。
2. **实际服务检查**：

   ```bash
   openssl s_client -connect collect.<真实域名>:443 \
     -servername collect.<真实域名> -showcerts \
     -verify_return_error -verify_hostname collect.<真实域名> -tls1_2
   curl --tlsv1.2 --tls-max 1.2 https://collect.<真实域名>/api/collect/readiness
   ```

   上述普通命令只检查当前测试客户端；还需在 `s_client` 配上目标根集，或将实际 leaf/intermediates 用 `openssl verify` 验证。不要使用 `curl -k` 作为验收。
3. **SSL Labs**：看发送链、替代路径、客户端握手模拟；它不能替代厂商浏览器、MTC 网络和 Web67 执行测试。
4. **真机矩阵**：至少 Android 5.1.1 一台、原 Android 6 红米 Note 4、原 Android 7 荣耀 Note8，以及一台正常现代设备；记录真实浏览器包名/版本、WebView、时间、代理、TLS 错误和后端 pair ID。
5. **业务终点**：同一浏览器能 GET 页面、加载所有本地 JS、POST Browser67、查询状态，且 App receipt/hash 与 Browser receipt/hash 在同 batch 中绑定为 `pair_status=completed`。页面打开或 HTTP 200 不是完整配对验收。
6. **续签后复测**：更换 leaf/issuer 后重新执行路径与站点检查；至少保留一个旧浏览器回归入口。Nginx reload 不应重启 backend 或切换 collection batch。

### 3.5 CA 选型及续签

ZeroSSL 的优势是现有官方交叉签名路径与 ACME；本次验证支持把它作为首选试点，而不是承诺其品牌覆盖所有旧机型。ACME 要显式指定 ZeroSSL directory，准备 EAB，固定 RSA key 类型，并配置续签后的链处理与 reload hook。[ZeroSSL ACME 文档](https://zerossl.com/documentation/acme)

可以评估提供明确 legacy bundle 和支持承诺的 Sectigo 商业 DV；其信任基础与 ZeroSSL 有关联，付费并不会绕过同样的根库问题。也可以要求 DigiCert/GlobalSign 供应商给出具体 RSA 链样例后做同一套验证，但本次没有足够证据说它们更适合。GlobalSign 也正进行根与证书 profile 调整，不能把老兼容表当成未来续签保证。[GlobalSign 根变更公告](https://support.globalsign.com/ssl/upcoming-changes-tls-roots-and-certificate-profiles)

Let’s Encrypt 当前标准兼容边界仍要求目标信任 ISRG 根，旧 Android 兼容交叉签名方案已经结束；仅更换域名再签一张同类 LE 证书，不解决本项目外部浏览器的目标约束。[Let’s Encrypt 交叉签名到期说明](https://letsencrypt.org/2023/07/10/cross-sign-expiration)

首期不需要 Redis、消息队列、Kubernetes 或训练容器。Compose 只是交付和进程管理手段；若希望最快验证 HTTPS，也可先以宿主机 Nginx + systemd/Uvicorn 做隔离预验，但正式环境只选一套管理方式。

### 4.1 容器网络和公网边界

- Nginx 改为 `proxy_pass http://backend:8000`，保留原完整 `/api/collect/...` 路径。backend 在容器内监听 `0.0.0.0:8000`，Compose **不写** `8000:8000`。容器内监听全接口不等于发布公网端口。
- 私有 bridge 只连接 Nginx/backend；若实际配置 `internal: true`，需要另给 Nginx 公网接入网络，让 ACME 客户端具备必要出口。不要把“无 ports 映射”与“internal=true”当成同一个概念。
- Uvicorn 信任真实 Nginx 地址/专用容器子网。不能继续只信任 `127.0.0.1`；否则 `request.url_for()` 可能生成 HTTP URL，浏览器被 mixed content 拦截。Nginx 覆盖 Host、`X-Forwarded-Proto` 和来源头，拒绝未配置的 Host；宽泛信任 `*` 只应在彻底隔离且唯一可信代理可访问的前提下考虑。[Uvicorn settings](https://www.uvicorn.org/settings/)
- 继续使用当前精确路由白名单，不能简单代理所有 `/api/*`，否则 `/api/agent/analyze` 等非采集接口也会被开放。
- Docker 发布端口可能绕过常见 UFW 路径，应结合腾讯云防火墙和 Docker 规则从外网验证 8000/5432 不可达。[Docker 防火墙说明](https://docs.docker.com/engine/network/packet-filtering-firewalls/)
- backend recreate 后容器 IP 可能变化；使用所选 Nginx 版本支持的服务名重新解析方案，或部署脚本在 backend ready 后 reload Nginx，避免旧 upstream IP。

### 4.2 必要但不过度的防护

SSH 使用密钥；确认普通 sudo 账号能登录后再禁 root/密码登录，22 限管理员来源。公网 80 只承载 ACME challenge 和跳转，正常采集只用 HTTPS；首次无证书时先启动 challenge 配置，避免 Nginx 引用不存在的证书无法启动。

保留现有 10 MiB 上限可作为第一步，它远高于现有约 22 KB 归档行；按真实最大请求及余量再收紧，例如验证后考虑 1 MiB。设置 header/body/read timeout、有限连接数、分接口 rate limit。App 上传和 ticket 当前没有操作员认证，Bearer token 只保护后续 Browser 流程；攻击者仍可申请合法 ticket 或写入伪造 App 数据。因此它是需要基本防滥用的公网写入服务。

限流要考虑云测平台共享 NAT：不要把每 IP 的低限额误当成每台设备限额。状态轮询和新 ticket 应分别配额；先观测再收紧。CORS origin 白名单不等于认证，仍可由非浏览器客户端直接请求。

Nginx 只挂静态 public 目录，禁止把仓库/data 暴露为站点根。容器用非 root 应用用户、数据卷明确 UID/GID；证书/key 目录只读挂给 Nginx。挂载整个证书目录，而非单个可能被续签工具原子替换的文件。日志不记 Authorization/token；保留当前 fragment 传票据方式。Docker 日志可先设 `max-size=10m`、`max-file=3`，Nginx 独立配置轮转。

`.env` 只存部署参数；密钥/ACME EAB 文件不进 Git，文件权限限制并另作加密备份。Compose 的项目 `.env` 不会自动把所有变量注入容器，需要显式 `environment` 或 `env_file`。不需要首期加复杂 secrets 平台。

### 4.3 数据可靠性与最小备份

现有代码有明确的可靠性缺口：

1. [main.py:2442](/Users/xavier/毕业设计/RBA-Cross-Device-Fingerprint/backend_server/main.py:2442) `save_to_jsonl()` 没有显式 `fsync`，App raw、analysis、receipt 走此路径；关闭文件不等于数据已经稳定写到磁盘。
2. [main.py:2232](/Users/xavier/毕业设计/RBA-Cross-Device-Fingerprint/backend_server/main.py:2232) 对 merged JSON 直接 `open(..., "w")`。中途崩溃可留下截断文件，下一次 `load_session_db()` 解析失败。
3. App 的多文件写入和 [main.py:1785](/Users/xavier/毕业设计/RBA-Cross-Device-Fingerprint/backend_server/main.py:1785) Browser 的三个追加不是一个事务。Browser 虽逐个 `fsync`，中途失败仍可留下部分记录；内存先变更再失败还会影响后续去重。这里是在识别故障窗口，没有证据说明当前 347 个配对已损坏。

上线前应至少把关键 append 改成可靠写入、merged JSON 改为临时文件+原子替换并正确处理目录持久化，明确异常时的内存状态与重试行为，增加启动对账/尾部不完整记录的隔离策略。不能把 `fsync` 或原子替换宣称为多文件事务；持续采集时 SQLite 事务可更彻底解决这个问题。

最小备份分两层：

| 内容 | 频率/保留建议 | 说明 |
|---|---|---|
| 采集中 raw、receipts、events、provenance 增量 | 每 15–30 分钟送异机，保留 48 小时的时间点 | 若没有写入屏障，只能叫恢复材料，不能保证是同一时刻完整快照。 |
| 完整一致备份 | 每个采集批次结束后立即；至少每日一份 | 暂停新任务、排空、正常停服后备份整个数据目录及配置版本。 |
| 完整备份保留 | 日备份 14 份、周备份 8 份；验收完成的正式研究批次长期另存 | 按磁盘/隐私要求调整，不能让本机备份挤满系统盘。 |
| 私钥、ACME 账号、必要 HMAC key | 初次配置及变更后加密异机备份 | Profile HMAC key 若用于离线稳定 ID，继续在离线环境单独保管，无须上传采集云。 |

要实现不切 batch 的“每 15–30 分钟一致快照”，需小范围新增**单 worker 进程内的写入屏障/快照功能**：在请求写入之间固定已提交边界、复制可变 JSON、记录每个 JSONL 的安全字节边界，随后由脚本复制对应前缀并上传异机。它目前不存在。可先采用批次结束备份；不能把正在写入时直接 `tar/rsync` 的结果宣传成事务一致备份，也不应每 15 分钟重启 backend 来做备份。

异机目标至少一个始终在线、与该系统盘独立的存储，例如私有对象存储或另一台服务器；Mac/外置盘作为另一份。Mac 睡眠时同步不可达，因此“只定时复制到 Mac”无法保证无人值守保护。`/opt/rba/data/backup` 仍在同一块盘，不防磁盘损毁；云磁盘快照可补充，但不替代异机和应用一致性。

恢复流程：停接新任务 -> 保存故障目录 -> 下载最近一致快照及增量 -> 恢复到新目录 -> 只读检查 JSONL/receipt/capture/pair 关联并隔离未完成记录 -> 以相同代码版本、单实例启动 -> 验证 readiness/新 batch -> 真机完成一轮 -> 切流。先在独立目录演练一次恢复。日备份本身的最坏丢失窗口可达一天；更短 RPO 要以增量对账或一致快照恢复测试为证。

若未来引入 PostgreSQL，增加每日 `pg_dump -Fc`（高采集频率下相应缩短间隔），与 raw artifact 的已提交边界一起记录；恢复为先还原 raw、恢复 DB、核对引用再开服务。不能只备份数据库或直接复制正在运行的 PG 数据目录，也不能认为每日 dump 提供 15 分钟 RPO。

### 4.4 运维及在线/离线职责

`git pull && docker compose up -d --build` 只是一组部署命令，不是足够的发布流程。需要固定版本、提前构建、暂停/排空、备份、切换、验收和回滚；仅在空闲窗口执行后端更新。不要部署自动拉取最新版并重启的工具。

值得增加：固定依赖、`.env.example`、数据 bind mount、`restart: unless-stopped`、合理 `stop_grace_period`、healthcheck、日志轮转、ACME renew/reload hook、备份 timer 和一个串联检查的部署脚本。Docker 由宿主机 systemd 启动即可，无须再用 systemd 另拉一份 Uvicorn。healthcheck 失败本身不等于容器一定自动重启；不能用无脑重启循环代替故障告警和数据检查。[Docker restart policy](https://docs.docker.com/engine/containers/start-containers-automatically/)

现有 `/health` 只返回存活，`/api/collect/readiness` 的顶层 status 固定为 ready；至少同时检查 batch=open、目录正确，并补充低磁盘/存储故障状态，不能仅凭 HTTP 200 判定可采集。

当前采集请求不执行 pandas、RF/MLP 训练；会同步做 JSON 处理、归档和配对。另挂载的 `/api/agent/analyze` 会同步执行规则、证据和检索逻辑，见 [agent_runtime_api.py:241](/Users/xavier/毕业设计/RBA-Cross-Device-Fingerprint/backend_server/agent_runtime_api.py:241)。推荐采集部署关闭或不公开它。云端接收与本地离线研究的分工合理。

## 5. Migration Plan

### Phase 1：先证明 HTTPS 路径

购买/配置真实域名与香港服务器，先直连 A 记录到自控 Nginx；不加会重新终止 TLS 的 CDN。若发布 AAAA，必须验证对应 IPv6 入口同样可达且链一致。申请 ZeroSSL RSA leaf、根据实际 issuer 配套 fullchain；用隔离静态页和隔离 backend 验证第 3 节矩阵。此阶段不触碰 Mac 正式目录。

验收条件是旧 Android 外部浏览器可完成页面和 API 流程。若 USERTrust 短链失败，再根据设备实际根库和链错误测试 AAA 扩展路径，不能先把任何失败都归为 CA。

### Phase 2：做小范围部署适配

- 修正 PID 判断：当前 [recover_unclosed_collection_batches():690](/Users/xavier/毕业设计/RBA-Cross-Device-Fingerprint/backend_server/main.py:690) 仅用保存的 PID + `os.kill(pid, 0)` 判断活进程。
- 本次抽取仓库实际函数，令遗留 PID 被当前活进程重用，已经复现错误阻止恢复。典型容器重启前后 Uvicorn 都为 PID 1，故会误判；加 `init: true` 也不是通用修复。
- 应使用持久目录上的独占进程锁等机制保证真实单写者，获得锁后才处理旧 marker；PID 保留作诊断。不要通过每次启动删除 marker 的方式掩盖并发或异常关闭。
- 加固第 4.3 节写入与恢复；至少验证正常停止、异常退出重启、磁盘写失败/重试、不启动第二实例四类边界。
- 处理 Agent import、依赖锁、CORS 和健康检查；新增 Compose/镜像，配置 `/data` bind mount。
- 确认 Nginx/后端容器代理信息正确，返回的 Browser upload/stage URL 必须是公网 HTTPS，不得为 `http://backend:8000`。

此阶段属于建议实施内容，本次没有修改。

### Phase 3：交付新 APK 与静态站

从当前已验证的 TLS 修复基础构建，显式设置四个地址，而不是只改 collect endpoint：

```text
hybridguardRequirePublicEndpoints=true
hybridguardCollectEndpoint=https://collect.<真实域名>/api/collect/fingerprint
hybridguardBrowserTicketEndpoint=https://collect.<真实域名>/api/collect/browser-ticket
hybridguardBrowserPairPollBaseUrl=https://collect.<真实域名>/api/collect/browser-pairs
hybridguardBrowserProbeBaseUrl=https://collect.<真实域名>/
```

配置 backend `HYBRIDGUARD_BROWSER_PROBE_ORIGINS=https://collect.<真实域名>`；过渡期确需旧页才额外保留 GitHub Pages origin。发布 `browser_probe_site/public/`，保留 canonical Web67 revision/manifest 合同，不为部署更换采集算法。

旧 APK 固定指向 ngrok/GitHub Pages。**它必须更新地址并重新分发，或有已经验证的配置覆盖机制。** 让旧 HTTPS 入口 301 到新域名不能修复旧入口的 TLS 失败，因为握手先于 HTTP redirect。只把 ngrok 后面的 FastAPI 搬到云上也不会改变 ngrok 给浏览器提供的证书。

### Phase 4：有暂停窗口的数据切换

1. 冻结代码/APK/静态页版本；保留旧镜像/配置。先构建完成，避免停服后才下载依赖。
2. 暂停云测新设备、新 session/ticket；给在途 App/Browser 配对排空窗口。超时的设备记录为待重采，不能伪造 completed。
3. 正常停止 Mac backend，确认 batch 关闭；整个 `mtc_20260917` 目录做一致备份并复制到云端独立持久目录，例如 `/opt/rba/data/collection_runs/mtc_20260917`。
4. Compose 中映射其为 `/data`，显式设置 `HYBRIDGUARD_DATA_DIR=/data`，核对权限。不复制 macOS venv，不只复制 raw/merged 中某一个文件。
5. 云端只启动一个 backend，记录新的 collection batch。历史已完成记录保留；在途 token/pair 的内存状态不能随文件复制恢复。
6. 停用旧入口的新采集或明确其过渡路由，避免 Mac 和云端同时接收同一任务形成两套数据。

若选择历史数据留 Mac、云端从新目录采集，也可行，但必须明确划分数据目录/批次并在离线合并时保留来源；不能把仅有新目录的云端称为已迁移全部历史数据。

### Phase 5：验收与扩大采集

外网 readiness 检查 -> 静态资源可用 -> App177 receipt -> ticket -> 实际浏览器 -> Browser67 -> `pair_status=completed` -> 两端 raw/receipt/hash/batch/provenance 关联完整。隔离预验目录的数据不得混入正式实验样本。

在隔离容器/测试卷做异常退出恢复、续签 reload、备份还原和逐级并发测试，再恢复批量采集。不能对正式采集进程做故障注入。

### Phase 6：回滚

切流前保留旧应用版本、配置、数据一致快照。失败时先停止新采集和云端写入，保存云端新增数据，避免覆盖回旧备份造成丢失；再还原兼容代码/目录，启动单实例和新 batch，重采在途设备。

优先让新的 `collect.<真实域名>` Nginx 保持在线，只回滚 backend 镜像；这样 APK 地址不变。若连域名/入口也回退，则要考虑新 APK 固定地址和旧入口的 legacy TLS 限制，不能宣称无缝回滚。回滚到 ngrok 并不等于旧浏览器问题仍然解决。

## 7. 风险列表

严重度针对拟上线方式；不表示这些事故已经发生。

| 级别 | 风险 | 具体依据/处理 |
|---|---|---|
| Critical | 单盘损坏丢失全部新增研究数据 | 本机 backup 不能防同盘损坏；上线前必须有异机副本及恢复演练。 |
| High | 旧浏览器无法验证实际 fullchain | AOSP CA 路径已通过，真实 leaf/OEM/浏览器/网络未测；以真机完整配对放行。 |
| High | 续签换 issuer 或丢 cross-sign，兼容性回退 | 固定 ACME provider/key type，续签后重新建链验证，证书到期告警。 |
| High | 容器异常重启被旧 PID 阻止 | 现有实际函数已复现 PID 重用误判；改独占锁后验收。 |
| High | 断电/写失败导致 raw/receipt/merged 不一致 | App append 无显式 fsync、merged 原位覆盖、多文件非事务；做恢复边界加固。 |
| High | 多实例或多个 worker 竞争数据目录 | 现有内存状态与 JSON 模型不支持；数据库未接入前固定一实例一 worker。 |

| High | 部署重启中断在途配对 | 新 batch、内存 pair 丢失；暂停/排空后发布，未完成设备重采。 |
| High | 公网写入被滥用或伪数据污染 | App/ticket 未认证且可占内存和磁盘；路径/体积/频率限制、容量告警，必要时再引入采集任务准入。 |
| Medium | 2 GB 内存随会话/票据增长 | 全量 session 加载、pair map 未见淘汰；监控和分批次归档，随后评估 SQLite。 |

## 8. 最终建议

选择 **B：原方案合理，但需要关键修改**，最重要的五点是：

1. **同域自控 HTTPS 是正确方向，ZeroSSL RSA 有可验证的候选链。** 本次已经验证 AOSP 5.1.1/6/7 的信任根和 CA 路径；上线承诺必须等真实域名与旧机型 paired244 验收。
2. **暂时去掉 PostgreSQL。** 2C2G 能作为纯采集单机起点；数据库改造应解决明确事务/恢复问题，后续优先 SQLite，不与 HTTPS 切换混成一次大重构。
3. **先处理实际代码缺口。** PID 重用误判、App 持久化、merged 原位覆盖、代理 scheme 和 Agent sibling import，都有具体源码依据。
4. **把续签与异机恢复纳入上线验收。** 一次 TLS 成功或一次容器启动成功，不等于后续自动续签和故障恢复能持续工作。
5. **按采集批次切换和回滚。** 现有 batch/token 绑定决定它不是无缝热迁移；新域名通常要求新 APK，旧 ngrok/GitHub HTTPS 入口的 redirect 不能绕过握手失败。

建议执行顺序：**真实域名/证书旧机型预验 -> 小范围存储与容器适配 -> 恢复/续签验收 -> 更新 APK -> 暂停窗口迁移 -> 扩大采集。** 当前没有必要提前购买更大的服务器，也没有依据保证只购买域名、安装 ZeroSSL 后所有旧系统错误都会消失。
