# WebGL1 同批数据八条容量验证

状态：**COMPLETE — 本批受控开发数据上的容量验证通过**。按事前协议完成12次新拟合、756次新留出预测，无失败、重试或追加模型。八条容量下，BASE49仍为 **117/126（92.86%）**，WEBGL50为 **126/126（100%）**，提高 **9条、7.14个百分点**；两组配对对照报警均为 **0/252**，没有配置退化或明确输出损失。

此前七条实验已提交推送至 `origin/main`，提交为 `9923cc74a4f3d359388ebcb40e5d104d05053941`。本轮遵循用户“先提交推送，再进行下一步验证”，回答：两组同时放宽到八条以后，WebGL1 能否补上 WebGL-only，又保留屏幕参数及其他配置的检出？

原七条模型的单文字规则每条复杂度为2，因此八条需要复杂度16；只将数量改为8、保留复杂度14仍然容不下第八条。语法中的最大已选规则数也同步为8。其余最大文字数12、最大不同原子数12、每家族最多2条、OP05、支持与覆盖要求、复杂度惩罚、语义排序、GREEDY和R_KEEP算法均保持不变。新条件没有额外奖励或强制入选。

八条使用独立的 `W0_CAPACITY_8_V1` profile、实验身份和模型schema。原CAP7模块和结果保持只读；本轮不能加载旧模型作为初始化，也不能跨组或跨折初始化。

## 输入与执行

只读复用 [上轮已准入输入](../webgl1_fresh_comparison_v1/prepared/PREPARATION.json) 的378条记录：126条受控干预、252条配对对照。原来的3条安装冒烟继续排除；没有新采集、重新生成候选、筛除未知值或修改标签。

两组使用完全相同的三个整环境留一折，每折252条训练、126条留出。先使用训练成员拟合并保存/重新加载模型，再打开留出输入；预测文件关闭后才关联留出标签。两组分别运行本轮GREEDY和R_KEEP，共 **12次新拟合、756次新预测**，这是比较结构需要的调用数量，不是沿用旧累计预算。

每个worker最多90秒，总worker时间最多1080秒；失败或超时即保存失败并停止剩余模型任务，不重试或临时调参。完整协议见 [PROTOCOL.json](PROTOCOL.json)。入口为 [run_comparison.py](run_comparison.py)，跨容量的保存结果复核为 [review_capacity_effect.py](review_capacity_effect.py)。

## 实际选中了什么

八条WEBGL50三个折均保留语言首项、新webdriver、WebGL1和屏幕DPR条件。与七条WEBGL50逐折比较，原七条全部保留，仅增加屏幕DPR条件。GREEDY在第八次添加时选入该条件，随后R_KEEP没有再调整。

八条BASE49最终也使用八条：GREEDY仍停在七条，原因是没有进一步提高其目标值的选择；R_KEEP按原有信号保留逻辑增加 `hardware_concurrency` 条件，使训练信号保留指标D从约1.3571提高到1.7143，但没有增加本批留出样本检出。这是保存轨迹中可见的冗余覆盖，不能把D提高当作检出率提高。两个八条模型的复杂度均为16。

这里屏幕、硬件并发数等数值阈值是各折训练得到的受控对照条件，不是浏览器官方不变量，也没有据此宣称它们可直接作为正常App人群的通用攻击规则。
