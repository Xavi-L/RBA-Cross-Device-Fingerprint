## 进一步核查出的硬性阻碍

[COVERAGE_FEASIBILITY.md](COVERAGE_FEASIBILITY.md) 和对应JSON记录独立推导。
原算法使用三值OR：包含一个U的OR不可能成为F；只有其他条件产生T时它才可判断，
而正常前后态上的T会占用clean报警预算。历史正常前后态的webdriver全部是U，
新raw观察没有改变这些历史事实。

因此，包含新webdriver条件时，每个clean阶段的可判断条数至多为
“webdriver已知条数＋整个clean报警预算”。即便把同一个总预算宽松地重复分给
pre和post阶段，四折的覆盖率上界仍为：

| 留出环境 | clean阶段覆盖率上界 | 所需覆盖率 | 两阶段至少需要的clean报警 / 允许预算 |
| --- | ---: | ---: | ---: |
| env-001 | 11/51 = 21.57% | 80% | 70 / 5 |
| env-002 | 11/54 = 20.37% | 80% | 76 / 5 |
| env-003 | 8/21 = 38.10% | 80% | 22 / 2 |
| 新raw环境 | 5/54 = 9.26% | 80% | 88 / 5 |

这严格排除了当前四折中包含该新条件的合法主OR模型。组合组仍可能学到不含该
条件的模型，整体检出率仍未知；但不能再把这份16fit草案当成让新webdriver入选的
可行方案。新执行入口据此阻止启动，而不是花训练次数再次验证这个已知限制。

下一步更合适的是单独准备原始观察完整的多来源开发集：保留现有新环境，再补至少
一个不同来源环境的相同三态采集，使每次留出raw环境时，训练端仍有完整raw支持。
历史162继续作legacy参考，不混入该raw训练集来制造大量U。即便这样仍需重新登记
分割和预算，且不等于总体泛化已获证明。不得靠重复同一环境来稀释U比例、把U改F、
降低80%门槛或自动改变AND/OR结构；这些都不是本轮授权的准备修复。
新增来源也必须先核对真实可用性；API不存在或读取异常仍保留U，不通过筛掉这些
样本来制造完整观察或泛化效果。
